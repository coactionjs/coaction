# Upgrading to Coaction 4.2

Coaction 4.2 hands the elements of state arrays out as the frozen values they
are, returns a copy from `getInitialState()`, and adds whole selectors to
`@coaction/react`. No API was removed. The changes show in how often some
`observer()` components render, in how a write outside `set()` fails, and in
what `getInitialState()` returns.

## Nothing to do for most applications

If components read the state through selectors or `observer()`, every write
happens inside `set()` or an action, and no test expects the message of a write
outside `set()`, there is nothing to change. Stores bound to another runtime
through an adapter, such as `@coaction/mobx`, `@coaction/pinia` or
`@coaction/zustand`, read their state as before.

## Array elements are values

An element read from the state of a native store -- by index, found by a scan,
or returned by a getter -- is the element itself, frozen, not a readonly proxy
of it. It is the same object however it was reached, `getPureState()`
included, so it can be compared, used as a hook dependency or passed as a prop
as it is. Objects reached through object keys are still readonly proxies.

An object can be held in both places: `{ selected: item, items: [item] }`, or a
recipe that sets `this.selected = this.items[1]`. It has one public identity, so
`state.selected === state.items[0]` holds as it did in 4.1, and that identity is
the first it was read with. Read through `state.items` first, it is the frozen
element at both places, and a reader of `state.selected.name` depends on the
element's identity. Read through `state.selected` first, it is the readonly proxy
at both places, including in scans, which then read that array through its proxy.
It compares equal to `getPureState()`'s object only in the first case.

An element with an accessor is not frozen either, since freezing leaves its setter
working: it stays a readonly proxy, and scanning its array reads through the proxy.

An array at an object key is not frozen: its readonly proxy guards it, and only
what it holds is frozen. An array held inside another array is an element, and
is frozen with it.

### What a reader depends on

A reader depends on the identity of each element it reads. Structural sharing
gives an element a new identity when anything inside it changes, and leaves its
siblings as they are. Objects reached through object keys keep their
per-property tracking: a reader of `state.user.name` still ignores a write to
`state.user.age`.

Read-only array methods -- `filter`, `map`, `find`, `some`, `reduce`, `slice`,
`for...of` and the rest -- take one dependency on the array and run over the
array itself, instead of tracking each element they visit. State read inside a
callback is still tracked. The dependency is on the whole array even for a method
that stops early or reads one element, such as `find` or `at`, and for an iterator
that is not read to its end: an `observer()` that renders `state.todos.at(0).title`
re-renders after a write to `todos[1]`. `state.todos[0].title` depends only on
`todos[0]`.

For a store holding `todos: [{ title, done }, ...]`, these components re-render
after a write to:

| Component                                                               | 4.1                   | 4.2                    |
| ----------------------------------------------------------------------- | --------------------- | ---------------------- |
| `observer()` rendering `state.todos[0].title`                           | `todos[0].title`      | anything in `todos[0]` |
| `observer()` rendering `state.todos.filter((todo) => todo.done).length` | any `done`            | anything in any todo   |
| `useTodos((state) => state.todos[0].title)`                             | `todos[0].title`      | `todos[0].title`       |
| `useTodos((state) => state.todos.filter((todo) => todo.done).length)`   | a change of the count | a change of the count  |

Where an `observer()` component now renders more often than it should, read
what it needs through a selector. A selector runs again when an element it read
changes, but re-renders the component only when its result changes, which is
what 4.1 rendered:

```tsx
const title = useTodos((state) => state.todos[index].title);
const doneCount = useTodos(
  (state) => state.todos.filter((todo) => todo.done).length
);
```

### Writes outside `set()`

A write outside `set()` never changes the state, but how it fails depends on
what it targets:

- An object reached through an object key is a readonly proxy. Writing to it
  throws Coaction's error, as before:
  `Direct state mutation is not allowed in immutable Coaction stores.`
- An element is frozen. In strict-mode code, which includes every ES module and
  class body, writing to it throws the engine's `TypeError`, such as
  `Cannot assign to read only property 'done' of object`. In a sloppy-mode
  script the write is silently ignored.

A test that expects Coaction's message from a write to an element should expect
a `TypeError` instead.

### Plain data before the first read

A store freezes the values of its initial state when it first hands one out
through the state. Until then -- and in a store read only through
`getPureState()` or whole selectors -- that data is not frozen. It is still the
store's own data: read it, never write to it.

### Adapter and binding authors

`trackReadonlyStateValue()` from `coaction/adapter` reports an element read from
the state as state, and `getReadonlyStateValueVersion()` gives it a constant
version: an element never changes, a write replaces it. A result that carries an
element therefore keeps propagating the element's changes, even where result
equality calls the result unchanged.

### Arrays with a custom prototype

`create()` and `setState({ ... })` copy an array as a plain array, so a custom
prototype reaches the state only through a recipe that assigns the array,
`draft.rows = rows`. Keep state in plain arrays: on such an array, these differ
from 4.1:

- A method of the prototype named like a read-only array method -- `map`, `find`
  and the rest -- reads as a wrapper rather than as that function, and runs with
  the array itself as `this` rather than its readonly proxy. So does the
  `constructor` that `map`, `filter`, `flat` and `flatMap` read.
- An element or a named value that the array only inherits is not guarded: it is
  not state, and a write to it is neither rejected nor noticed.
- An array whose `Symbol.isConcatSpreadable` is `false` joins a `concat()` as the
  array itself rather than as its readonly proxy.

## `getInitialState()` returns a copy

A native store kept the object its factory returned and gave it back from
`getInitialState()`, which held all of the initial data a second time for as
long as the store lived. It now keeps only the factory's methods, accessors and
computed definitions. The first call to `getInitialState()` builds a copy of the
store's initial data shaped like the factory's object -- the same keys and
attributes, the factory's own functions, and data equal to what the factory
returned -- and every later call returns that same object. Changing it does not
change the store.

`store.setState(store.getInitialState())` resets the store. Given that object,
`setState()` takes its data and leaves the methods, accessors and computed
values beside it, which 4.1 rejected as unknown state keys.

Code that compares `getInitialState()` with the factory's object by identity,
or changes the factory's object to change what `getInitialState()` returns,
needs to change. Stores bound to another runtime return what that runtime
provides, as before.

## An array's state is its elements

Named keys and symbols on an array -- `Object.assign(rows, { meta })` -- are not
state. A recipe's first write to such an array has always dropped them, without
a warning, because Mutative and Immer copy only an array's elements. Until then
the store kept them, so what a reader saw depended on whether a write had
happened. Now `create()` and `setState({ ... })` copy only the elements from the
start, and warn once in development (`NODE_ENV=development`).

If you keep a value on an array, keep it in an object beside the array instead:
`{ rows, rowsMeta }`. A recipe that assigns an array, `draft.rows = rows`, stores
it as it is, and its named keys last until the first write to it. They are not
frozen with the array, so a value read from them can be changed without an error.

## Whole selectors

`@coaction/react` adds `useStore(selector, { whole: true })`. A whole selector
runs over the store's plain data, `getPureState()`, without getters or methods,
and records no dependencies: it runs again on every commit, and re-renders the
component when its result changes by `Object.is`, or by an `equals` passed
beside `whole`. It is opt-in; selectors without it keep tracking what they read.

The data a whole selector receives is the store's own, neither a readonly view
nor necessarily frozen: read it, never write to it. A selector that builds a new
array or object on every run needs `equals`, or it re-renders the component on
every commit. The [React package README](../../packages/coaction-react/README.md)
has examples.

## What did not change

`Object.getOwnPropertyDescriptor()` and `Object.hasOwn()` remain outside tracking,
as in 4.1: neither takes a dependency of its own, and a descriptor's `value` is the
store's own data, not a readonly view. A reader that also reads a sibling is
therefore not notified when the key it asked about appears. Ask with `key in object`
instead, which depends on the keys of the object and not on the values of its
children, as `Object.keys()` does.

The content of patches, the JSON contracts of shared transport and remote
synchronization, and the wire protocol are unchanged, and so are objects reached
through object keys and stores bound to other runtimes.
