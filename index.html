The model

Immutable state. Signal-level reactivity. Transactional updates.

Coaction keeps React-style immutable snapshots and adds what they usually lack: fine-grained tracking on reads and reusable transitions on writes.

Immutable snapshots, natural writes

Write this.user.age += 1 inside set(). Mutative turns the draft into a new frozen snapshot, and untouched branches stay shared.

user└─ profile├─ name<UserName />└─ ageno readers

Signal-level precision on plain objects

Reads build a path graph on alien-signals. A reader of user.profile.name ignores a change to age, and your model needs no Signal<T> or Atom<T>.

Getters that cache themselves

A plain get total() is a cached computed value. Its dependencies are found automatically, and every reader shares one result.

Every write is a transition

set() produces the next snapshot and a commit, with patches when a feature needs them. Undo, persistence, sync and workers all build on it.

Live playground

Click an action. Count the re-renders.

This is the Coaction in this repository, running in your browser. Every cell is a component that counts its own renders: wrapped in observer() on the left, a plain useShop() that subscribes to the whole store on the right.

import { create } from '@coaction/react';

export const useShop = create((set) => ({
  user: { name: 'Ada', age: 36 },
  cart: { items: [{ name: 'Notebook', price: 12 }] },
  theme: 'light',

  get total() {
    return this.cart.items.reduce((sum, item) => sum + item.price, 0);
  },

  rename(name: string) {
    set(() => {
      this.user.name = name;
    });
  },
  birthday() {
    set(() => {
      this.user.age += 1;
    });
  },
  addItem(item: Item) {
    set(() => {
      this.cart.items.push(item);
    });
  },
  setTheme(theme: 'light' | 'dark') {
    set(() => {
      this.theme = theme;
    });
  }
}));

Less glue

The same counter, minus the selector plumbing.

A Coaction store reads like a Zustand store. What goes away is the code that only exists to stop extra renders: selectors, shallow equality and hand-written memoization.

  • No selector in the component
  • No dependency array for doubled
  • No manual memoization

Selectors, createSelector() and useStore(selector) stay available whenever you want them. Migrating from Zustand

Transitions

Every write is a transition you can reuse.

set() turns a recipe into the next snapshot and a commit. When a feature needs them, the commit carries patches and inverse patches, and undo, persistence, sync and shared runtimes all build on it instead of inventing their own write semantics.

Shared runtime

Start local. Move execution when you need to.

The same store source moves off the UI thread without a rewrite. A Worker becomes the authority, the page keeps a mirror for reads, and Coaction handles sequencing, patch sync and reconnects.

Fit

Coaction, Zustand or MobX?

Getters, this and automatic tracking are not new: MobX has shipped them for a decade. What is uncommon is having them on an immutable substrate, behind a Zustand-style create(), across five frameworks.

Honest answer

Most apps don’t need it.

For plain single-tab state with a few values, Zustand or Jotai is a smaller dependency with a bigger ecosystem. Coaction earns its place when you want several of these at once:

  • Immutable snapshots with automatic deep render tracking
  • Cached derived state without hand-written memoization
  • Mutable-looking writes that produce an immutable result
  • Undo, persistence or sync built on the same transitions
  • A Worker or SharedWorker as the authority for one state
  • Local-first remote synchronization
  • One model that grows without a second runtime

Know the costs: about 10.7 KiB gzip for the coaction consumer fixture with dependencies externalized, and roughly half of Zustand’s throughput when every update is followed by a read.
