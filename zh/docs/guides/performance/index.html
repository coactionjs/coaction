性能与 bundle 边界

根据版本、数据规模和读写模式解读基准结果，并检查应用使用的包入口。

比较吞吐量时，应注明运行环境、包版本、状态规模和操作顺序。仓库提供基准脚本，可用相同的工作负载复现结果。

运行维护的检查

  • package:size 检查发布入口预算与 core entry 隔离；
  • benchmark 对比大型 update path，包括 Coaction draft 与 Zustand + Immer；
  • benchmark:zustand-positioning 分离 stable derived read 与 update-then-read；
  • benchmark:check 校验绝对吞吐量下限和相对性能比值。CI 的 Ubuntu ARM 运行器对路径 effect 和 1,000 个元素各有一个读取者的写入测试使用单独标定的吞吐量下限。
  • benchmark:derived 在独立进程中使用构建后的入口，覆盖稀疏路径、相关／无关写入、全量扫描、缓存读取，以及尚未读取／已销毁的 owner。它已加入 benchmark:check；全量 deep scan 的结果用于展示追踪成本，原生 getter 提供 coarse scan 基线。

调整回归阈值时，应记录并评审运行时行为或测量方法的变化，以及支持调整的测量结果。

派生状态的读取与更新成本

依赖未变化时，访问器直接返回缓存结果。更新后首次读取派生值时，Coaction 还需维护公开状态的只读视图，并刷新计算使用的快照。两种工作负载应分别计时。

原生本地 store 可直接比较写入前后已追踪的路径，即使依赖集合较大也能使用这种方式。提交钩子、补丁中间件和计算快照缓存等会请求补丁。普通 subscribe() 订阅本身不请求补丁。需要为其他用途生成补丁时，可显式设置 enablePatches。

比较派生读取时应注明总值的计算方式。Zustand 可以把预先计算的总值保存在字段中，应用负责在相关写入时同步更新该字段。Coaction 的 getter 由运行时维护缓存。单项测试结果只适用于对应的工作负载。

渲染性能

原生 immutable store 上的 useStore(selector) 与 observer() 都使用可回收的深层路径追踪。读取 state.user.name 的 reader 可以在仅更新 age 的 recipe 后继续使用缓存。Selector 仍以 Object.is 比较结果；observer() 直接收集 render 中的读取，不需要额外 selector。请分别测量 selector 执行次数与组件 render 次数。

数组元素是值：reader 依赖它读取的每个元素的身份，filter、map 等数组方法只对整个数组登记一个依赖。渲染 todos[0].title 的 observer() 会在 todos[0] 内部的任何写入后重新渲染，渲染扫描结果的 observer() 会在任一元素被写入后重新渲染。返回该字段或扫描结果的 selector 会重跑，但只有结果变化时才重新渲染。

原生 getter 与 get(deps, fn) 仍以 store/slice 字段为边界。读取 this.user.name 的 getter 可能因 user.age 变化而重算，即使结果相同、消费者没有额外工作。需要更细依赖的派生读取可使用 derive(..., { deep: true }) 或 derivePath。

父对象 replacement、数组结构变化和 graph snapshot patches 可能扩大失效范围；外部 adapter 遵守各自的更新和快照 contract。具体边界见 computed 追踪粒度。

性能检查清单

  • Vanilla 本地状态导入 coaction；
  • 非必要时不设置 enablePatches，同时考虑会自动请求 patches 的消费者；
  • 缓存 getter 用于重复派生读取，不承载副作用；
  • 在确实减少 selector 组合时使用 observer()；
  • 若 observer() 会因元素中其他字段的写入而重新渲染，改用 selector 读取数组元素的字段或扫描结果；
  • 使用生产构建，在有代表性的数据规模和读写模式下进行性能分析。
  • 用基准阈值检测回归。对外报告性能数据前，应在目标硬件上重新测量。
